# Kev-0.6B in the extension: progress

Short bullets, appended at each gate. Tags as in research/kev-0.6b-browser.md: **[measured]** (done here, on this MacBook Air with an Apple M2 and 8 GB, Chrome 158.0.8127.88), **[not verified]** (not done, with the reason).

## Gate A (no browser), 2026-11-26

- **Done**
  - `tools/vendor-kev.mjs` fetches the runtime into `extension/vendor/` and refuses a hash mismatch; `--check` verifies offline. Each npm tarball is pinned by the sha512 that the registry publishes, each extracted file by its SHA-256. **[measured]**
  - `extension/src/ai/kev-manifest.js`, `tools/check-kev-manifest.mjs`: the commit, sizes and SHA-256 of all seven files were checked against the Hugging Face API for the pinned commit, and the SHA-256 of both large files (335,357,952 and 374,822,912 bytes) was computed again from full downloads (streamed, nothing kept): all equal. The delimiter ids and limits equal the `kev` section of the pinned `config.json`. `Range: bytes=0-15` answers `206` with the right `Content-Range` for every file, through the redirect to `us.aws.cdn.hf.co`. **[measured]**
  - `extension/src/ai/kev-core.js` (layout of the sequence, escaping, softmax, yes/no and level decoding) with `tests/kev-core.test.js`. Cross-checked once against the open-jev 0.1.2 package, installed in a scratch folder only: the same probability to the last digit on 10 inputs, with the real tokenizer and the real q4 model on the processor. The package is not a dependency. **[measured]**
  - `tools/eval-kev.mjs` and `research/kev-accuracy-smoke.md`. **Verdict: slightly better than the word lists alone on the cue-word titles, not clearly.** 16 more of 70 missed examples flagged (23 percent) for 2 false alarms in 20 spared lines; AUC 0.62 (95 percent interval 0.48 to 0.74, so it includes chance) on the lines where the engine asks the model, 0.73 on all lines. A statement form of the questions is worse, a form without the exceptions is slightly better. These are the rule author's own examples, not a labelled set. **[measured]**
- **Vendored size**: 41,807,988 bytes in `extension/vendor/` (the WebGPU WebAssembly binary 26.9 MB, the processor binary 14.3 MB, Transformers.js 0.59 MB, loaders, licences and the README). The extension zip written by `npm run pack` is 10,862,439 bytes (it was 91,125 bytes in release 0.2.1). The research's figure of 6.9 MB was for the WebGPU build alone; the processor build, which turned out to be needed, accounts for the difference (about 4 MB zipped, by subtraction). **[measured]**
- **The plan's 8,192-token claim is corrected** in plan.md (the model was trained on states of at most 384 tokens, and questions of at most 1,024); the extension cuts the text to 384 tokens.

## Gate B (browser spike), 2026-11-26

A throwaway extension in a scratch folder (own profile, port 9555, `--mute-audio`, killed afterwards), with the project's CSP (`script-src 'self' 'wasm-unsafe-eval'`, nothing else added), the vendored runtime, an offscreen document and a worker; the weights came from a local mirror (`tools/kev-mirror.mjs`) into OPFS, 40 of the rule examples were asked.

- **It works in this machine's Chrome 158 under the extension CSP.** No console error, no `EvalError`; the `new Function` that sits in the bundles was not reached on the WebGPU path or on the processor path. **[measured]**
- **WebGPU exists inside the offscreen document** of a `--headless=new` Chrome: adapter Apple M2 (metal-3), `shader-f16` present, `maxBufferSize` 4 GB. **[measured]** Two traps found on the way:
  - With the Mac's display asleep, the headless browser's DevTools port stopped answering (the log fills with `CVDisplayLinkCreateWithCGDisplay failed`). A time-limited `caffeinate -d` for the run fixes it. Not a WebGPU problem, an environment one. **[measured]**
  - A message listener in my own spike code that never answered made the offscreen document wait for ever; not a model problem. (Mentioned because it looked exactly like a hung GPU for a while.)
- **OPFS works from a worker of the offscreen document in the extension's origin**, with synchronous access handles. Writing 335 MB while hashing took 2.6 to 3.3 s of which the hash (my pure-JS SHA-256 in the worker, `extension/src/ai/sha256.js`) took 2.2 s: about 150 MB/s. `navigator.storage.persist()` answered false in headless Chrome (the `unlimitedStorage` permission is what protects the files). **[measured]**
- **Speed, per question of 33 to 84 tokens (title, rule question, options), 40 items, after loading:**
  - WebGPU, `q4f16` (346 MB set): load from OPFS 1.9 s, first answer 1.4 s (includes shader compilation), warm median 118 ms, p95 160 ms, max 228 ms. **[measured]**
  - WebGPU, `q4` (383 MB set, no half precision): load 2.1 s, first 1.1 s, warm median 131 ms, p95 185 ms. **[measured]**
  - WebAssembly on the processor, `q4`, one thread: load 1.5 s, first 1.7 s, **warm median 1.82 s, p95 2.58 s** (about 34 ms per token): usable for a background filter, 15 times slower than WebGPU. **[measured]**
- **The WebAssembly path needs a second ONNX Runtime build.** The "asyncify" build that serves WebGPU has no processor kernel for `GatherBlockQuantized` ("Could not find an implementation for GatherBlockQuantized(1)"), which the model's 4-bit embedding table needs; the plain processor build (`ort-wasm-simd-threaded.mjs` and `.wasm`) has it and runs the model. So both builds are vendored. **[measured]**
- **Answers across runtimes** (the same 40 items): the browser's `q4` on WebGPU and on WebAssembly give the same p (largest difference 0.00001); the browser's `q4f16` differs from them by at most 0.032 (mean 0.006); the Node run of the smoke test (onnxruntime-node 1.30.0) differs from the browser by at most 0.084 (mean 0.022). At the level 0.8, no item of 40 changes side between Node and the browser; at 0.5, 2 of 40 do. So the smoke test's numbers hold, with a noise of a few hundredths in p that the thresholds must tolerate (plan.md section 1 already says so). **[measured]**
- **Memory** (macOS `footprint`, which counts graphics memory, and `ps` RSS), with the session alive after the 40 answers:
  - WebGPU `q4f16`: offscreen renderer 758 MB (measured without a garbage collection first) and GPU process 712 MB. **[measured]**
  - WebGPU `q4`: renderer 357 MB and GPU process 721 MB (after a garbage collection). **[measured]**
  - WebAssembly `q4`: renderer 543 MB; GPU process 29 MB. **[measured]**
  - While loading, the offscreen renderer peaked at 1.1 GB (WebGPU) and 1.5 GB (WebAssembly) RSS, because the 335 to 375 MB weight file is read into one buffer and copied; the JavaScript heap holds about 415 MB until the first answer is done and about 40 MB afterwards (after a garbage collection; measured in the two `q4` runs). **[measured]**
  - On an 8 GB computer that is 1 to 1.5 GB for as long as the model is loaded, which is why the offscreen document unloads the model after a few idle minutes. **[CHOICE: 5 minutes]**
- **Cannot be seen from a headless run**: how a headful Chrome with a window and other tabs behaves; the owner sees it on the settings page (the Kev row says "Ready" with the way it runs) and in `chrome://gpu`, which lists WebGPU under its graphics feature status (that page was not opened here). **[not verified]**
- **Not measured**: threads for the processor path (needs cross-origin isolation through two manifest keys that would also change the settings page and the website's embedding of it; not enabled), memory pressure when other apps use the GPU, behaviour after a GPU reset, Windows and Linux.
- **Decision**: Phase C builds both paths: WebGPU (half precision when `shader-f16` exists, else `q4`), and WebAssembly (`q4`, plain build, slow).

## Gate C (the feature), 2026-11-26

- **Built** (all under `extension/src/ai/` unless named; the vendored runtime is in `extension/vendor/`)
  - Download manager: `kev-download.js` (pure logic: `Range` resume, a re-read of what is on disk through the hasher, retries, hash check, progress and speed), `kev-download-worker.js` (a dedicated worker of the offscreen document: OPFS synchronous access handles), `kev-store.js` (the files and `state.json`, which records what was verified), `sha256.js` (incremental, pure JavaScript). Pause, Cancel and Delete are messages to the service worker, which accepts them only from pages of the extension (`ai-router.js: fromExtensionPage`); the offscreen document accepts control messages only from the service worker.
  - Inference: `kev-offscreen.html`/`.js` (the router, the idle timer: the model leaves memory after five idle minutes, CHOICE), `kev-runtime.js` (load from OPFS, a warm-up question, one question at a time, a time limit of 60 s, WebGPU device loss), `kev-gpu.js`, `kev-backend.js` (the service worker's client, same surface as `prompt-backend.js` plus status, download, pause, cancel, delete).
  - Layers: `ai-ask` and `ai-status` of the service worker build the layer list [Kev, Chrome's model] and answer through `askLayered` (core/layered.js, contract unchanged); `ai-status` reports `layers`, `key` (changes when the set of models that can answer changes, so a tab forgets answers kept from other models) and `loading`; `content/main.js` re-polls every 3 s while `loading` and at once when the storage key `kevEpoch` changes (written when a download ends or the files are deleted). Setting `ai.backend`: `auto` | `kev` | `prompt` (`shared/config.js`, under `ai`, so "Reset to defaults" of the On-device AI pane puts it back). The decision to ask Chrome's model second only when Kev is not sure (0.35 to 0.65) is layered.js's CHOICE, unchanged; no threshold was retuned.
  - Settings page, On-device AI pane: the row "Kev-0.6B" first (states Not downloaded, Downloading with a bar, megabytes and speed, Checking, Paused, Ready with "Runs as: WebGPU, q4f16" or "WebAssembly, q4: slow", Failed with the file and the reason, Cannot run), then "Gemini Nano (built into Chrome)" with "Download Gemini Nano" and the picture and sound rows naming their model; `kevStatusInfo` in `core/modelcheck.js` (pure, tested); a "Models to use" choice; the panel "Check on the rule examples" (`core/examplecheck.js`, pure, tested): every rule's `example:` and `spared:` lines through the real engine, once with the word lists alone and once with the models, each line judged with itself left out of the examples that the engine shows the model; per rule and in total it says what the models flagged that the words missed (examples, good), what they cleared that the words flagged (spared lines, good), what they cleared that the words flagged (examples, bad) and what they flagged that the words left alone (spared lines, bad); Stop and progress; it runs on whatever lines the rules hold, so the lines the owner adds are counted. The click on Download asks for host permission first (before anything is awaited): `https://huggingface.co/*` and `https://*.hf.co/*` are `optional_host_permissions`.
  - Manifest: permissions `offscreen`, `unlimitedStorage`; `optional_host_permissions`; the extension-pages CSP is `script-src 'self' 'wasm-unsafe-eval'; object-src 'self';` and nothing else. The packed zip is 10.9 MB (was 0.09 MB), 42.5 MB unpacked, 145 files. **[measured: `npm run pack`]**
  - Tools: `tools/vendor-kev.mjs`, `tools/check-kev-manifest.mjs`, `tools/eval-kev.mjs`, `tools/kev-mirror.mjs` (a local stand-in for huggingface.co with redirects, `Range`, cut connections, a flipped byte, 503), `tools/kev-test-ext.py` (a test copy of the extension that names the local server).

## Gate D (documents) and final status, 2026-11-26

- **Done**: README.md (the section "The local model", the permission and storage facts, how to run the tests and the end-to-end scenario), plan.md (the 384-token correction in sections 3.1 and 8, what is built in section 10 with the calibration issue noted, Kev's measured accuracy in 3.1), this file and research/kev-accuracy-smoke.md.
- **What the owner decided and what was chosen without him (CHOICE)**
  - Decided by the owner: a first-run download of about 346 MB from huggingface.co with the host permission asked at download time; WebGPU first, a WebAssembly fallback; Kev first and Chrome's Prompt API model as the second look; no fine-tuning for now; the two spikes first.
  - Chosen here: the model is unloaded after 5 idle minutes; a question that takes more than 60 s makes the page drop the model, and the service worker gives up after 90 s; 3 failed attempts in a row, 1.5 s apart (times the attempt number), before a download stops with an error; the state is cut at 384 tokens and a question plus state at 1,024 (the trained values of the model's config, not the 8,192 of the graph); both ONNX Runtime builds are vendored (+14 MB) so that the processor path works; no threads for it (that would need cross-origin isolation); the sets are chosen from the graphics adapter at the click (`shader-f16` gives the 346 MB set, else the 383 MB set); `ai.backend` `auto`/`kev`/`prompt`; `ai.shots` 2 with the examples-first format (research/kev-accuracy-smoke.md); the test hook (a local server instead of Hugging Face) works only with the debug switch on and only for `127.0.0.1` or `localhost`; the layered thresholds 0.35 to 0.65 and every rule's `flag at` were not changed.
- **Not verified**: the optional-permission prompt in a headful Chrome; OPFS across a browser restart; Windows and Linux; memory use next to other heavy tabs; a real Gemini Nano as the second layer; accuracy on anything but the rule author's own lines; the speed of the processor path with threads.
- **To rerun**: `node --test tests/`; `node tools/vendor-kev.mjs --check`; `node tools/check-kev-manifest.mjs [--full]`; the smoke test needs a scratch folder with `@huggingface/transformers@4.3.2` and the model files (see the header of `tools/eval-kev.mjs`); the end-to-end run is in the header of `scenario_kev` in `tools/e2e.py` (a copy of the extension from `tools/kev-test-ext.py`, `KEV_FILES`, a Chrome started by `tools/e2e-chrome.sh` or by hand, the display kept awake with `caffeinate -d`).
